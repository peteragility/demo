1Target Use Cases — What to Lead With, and Why

Ordered by "existing Databricks footprint × ease of starting × natural growth". The first three are the activation engines.

🤖 1. Agent Memory Backend

Primary activation driver — every production agent needs one

Persist agent chat sessions/messages (users resume conversations, agents reason over prior turns across deploys) + structured task state + tool-call records. pgvector for memory retrieval.

Why we win: session/state is a transactional workload — it doesn't belong in Delta (no low-latency point reads); it's exactly Postgres territory. Suncorp's 16 production agents run this exact pattern.

⚙️ 2. Agentic Orchestration State

Sold together with #1 — task queues + checkpoints

Task queues, approval gates, human-in-the-loop checkpoints, shared agent sessions for multi-agent systems — all low-latency transactional state. Postgres-as-queue is a proven pattern.

Why we win: orchestration state must be transactional and share one governance surface. Add branching = agent dev-loop sandbox (experiment/rollback in O(1)).

📊 3. Real-time Feature Serving

For existing ML customers — zero new concepts

Online features for ML models: low-latency point reads + write paths fed by lakehouse batch features. Tables registered under the same UC governance.

Why we win: the feature-store online-store budget already exists (currently going to DynamoDB/Redis) — it's not new money, it's redirected money.

📱 4. SaaS / Data App Backend

High ACV — the entire app backend

Operational backend for Databricks Apps: user accounts, tenant configs, app state. 8TB/instance, PITR, pgvector, Postgres 17 — production-grade SaaS DB.

Why we win: app + analytics on one platform — user behavior writes land and are instantly analyzable by Spark/BI (zero ETL). Aurora customers can't do this.

🔁 5. Dev/Test Environments (Branching)

Quick win — sell branching, not migration

One-click branch of prod with real data (O(1), seconds), one branch per PR in CI/CD, dispose when done.

Why we win: dump/restore hours → seconds. The easiest PoC "wow moment" — no need to touch the customer's production DB.

🏦 6. FSI: Operational + Analytics Unified

Large deal size — longer cycle

Transactional/account workloads + instant risk/reporting on the same data — traditionally OLTP (Aurora) + ETL + lakehouse, two stacks. Lakebase: one.

Why we win: one dataset, one governance surface (UC) — the FSI compliance dream. Cross-region DR not yet at parity — handle honestly.

1bTargeting RDS / Aurora PgSQL / Azure SQL Estates — Where the OLTP Edge Is

Agentic and app backends grow the account; classic OLTP displacement grows the ACV. Not every OLTP workload is winnable — these four segments are where Lakebase has a real edge, plus the honest no-go zone.

📈 A. Analytics-Adjacent OLTP the biggest real edge

Applications whose transactional data also feeds reporting/BI/ML: SaaS with customer-facing dashboards, ops platforms with internal analytics, fintech transaction + risk/compliance reporting, IoT platforms with operational + historical views.

Edge: on Aurora/RDS/Azure SQL the data needs ETL (DMS/Glue/Factories) before analytics sees it — double storage, double pipeline, double ops. Lakebase: the same pages the lakehouse reads. One copy, one governance surface, zero ETL. Sell to the CFO as pipeline elimination.

🔁 B. Multi-Copy / Multi-Environment Estates

Enterprises running many copies of the same prod DB: dev/test/UAT refresh cycles, compliance-testing environments, per-release verification copies. A bank with 20 env copies pays 20x storage + compute on Aurora.

Edge: branching is O(1) metadata — every environment is a branch at storage cost, created in seconds, disposed freely. Typical candidates: financial services, healthcare, any regulated shop with heavy test-data-management overhead.

💤 C. Long-Tail / Spiky App Portfolios

The "200 small databases" estate: business-hours internal tools, region-specific apps, batch-driven jobs, seasonal apps. On RDS/Aurora each idles at minimum capacity 24/7 — thousands/month of dead spend.

Edge: true scale-to-zero + 300–500ms resume (Aurora v2: ~15s resume, no true zero). Consolidate the long tail onto Lakebase and the resume gap is invisible to users. Sell as portfolio cost consolidation.

🤖 D. OLTP Apps Adding AI Features

Existing Postgres applications modernizing with AI: adding copilots, RAG over business data, recommendations, agent features. The DB suddenly needs pgvector, agent state, and AI-adjacent workloads next to the OLTP core.

Edge: pgvector + agent memory + lakehouse grounding on the same platform as the OLTP core — and open-source Postgres (not a fork) means the app's SQL moves as-is from RDS/Aurora PgSQL. Azure SQL (T-SQL) is a rewrite — target the Postgres pool first.
🚫 Honest no-go zone (don't chase these): steady-state high-utilization classic OLTP with no analytics need (ERP-style, always-hot, 24/7 full load); workloads hard-requiring mature cross-region sync DR; workloads dependent on vendor-specific engine features (Oracle/SQL Server richness). These are Aurora/RDS/committed-license territory — spending cycles here loses deals and credibility. Qualify with one question: "does this app's data also need to be analyzed, copied, or made smarter?" If yes → segment A/B/C/D above. If no → walk away.
