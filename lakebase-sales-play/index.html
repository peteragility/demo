1Target Use Cases: What to Lead With, and Why

Ordered by "existing Databricks footprint × ease of starting × natural growth". The first three are the activation engines. Tags map to the four play types in the AE/SA brief: T1 lakehouse-adjacent serving · T2 agentic + app backend · T3 LTAP (OLTP + OLAP) · T4 OLTP takeout.

🤖 1. Agent Memory & Search T2

Primary activation driver: every production agent needs one

Persist sessions and messages (users resume conversations; agents reason over prior turns across deploys), structured task state and tool-call records. Recall them with Lakebase Search: vector, BM25 keyword or hybrid, in the same Postgres.

Why we win: session state is a transactional workload that needs millisecond point reads and writes, which Delta isn't built for. That's exactly Postgres territory. Memory, search and governance live in one database instead of Postgres + a vector DB + a cache.

⚙️ 2. Agentic Orchestration State T2

Sold with #1: task queues + checkpoints

Task queues, approval gates, human-in-the-loop checkpoints and shared sessions for multi-agent systems: all low-latency transactional state. Postgres-as-queue is a proven pattern.

Why we win: orchestration state must be transactional and share one governance surface. Add branching and you get an agent dev-loop sandbox: fork, experiment, reset in seconds.

📡 3. Lakehouse Data Serving T1

Fastest path to production: the data is already in UC

Serve curated Delta tables to apps, APIs and ML features in milliseconds: synced tables (snapshot / triggered / continuous) plus the PostgREST-compatible Data API. This replaces the Redis, DynamoDB or document-DB serving copy that teams build and babysit today.

Why we win: no pipeline to build, and one governance surface. The budget already exists, because it's paying for the serving copy. It's redirected money, not new money.

📱 4. SaaS / Data App Backend T2

High ACV: the entire app backend

Operational backend for Databricks Apps and citizen-dev apps: user accounts, tenant configs, app state. Up to 112 CU, HA with 1–3 secondaries, 6 read replicas, point-in-time restore (2–30 days), Postgres 16–18.

Why we win: app + analytics on one platform. App writes can stream to Delta through Change Data Feed (Public Preview), so behavior data lands in the lakehouse without a pipeline. Aurora needs a zero-ETL copy for the same thing.

🔁 5. Dev/Test Environments (Branching)

Quick win: sell branching, not migration

Branch production with real data in seconds (O(1), up to 500 branches per project), one branch per PR in CI/CD, reset from parent in one click, auto-expire with a TTL.

Why we win: dump/restore hours become seconds. It's the easiest PoC "wow moment", and there's no need to touch the customer's production database.

🏦 6. FSI: Operational + Analytics Unified T3

Large deal size: longer cycle

Transactional and account workloads plus risk and reporting on the same data. Traditionally that's OLTP (Aurora) + ETL + a lakehouse: two stacks. With Lakebase it's one, with PCI-DSS + HITRUST on AWS and a 99.99% SLA with HA.

Why we win: one dataset and one governance surface (UC), the FSI compliance dream. Cross-region DR is not GA yet, so raise it honestly and early.

📐 The fan-out rule

Big Lakebase spend comes in two shapes: many apps (a portfolio of internal or citizen-dev apps, each on its own database) or one app × many users (a customer-facing app, agent or search). Qualify for one of the two. A single small internal app rarely gets past $1–2K/mo.

🧭 Sell to the app team

Data teams buy tables; app and platform teams buy databases. If your only contact is the data team, you'll stall at reverse-ETL. Get introduced to whoever owns the app backend, the DocumentDB / Aurora / RDS estate, or the agent platform.

1bTargeting RDS / Aurora PostgreSQL / Azure SQL Estates: Where the OLTP Edge Is

Agentic and app backends grow the account; classic OLTP displacement grows the ACV. Not every OLTP workload is winnable. These four segments are where Lakebase has a real edge, followed by the honest no-go zone.

📈 A. Analytics-Adjacent OLTP the biggest real edge

Apps whose transactional data also feeds reporting, BI or ML: SaaS with customer-facing dashboards, ops platforms with internal analytics, fintech transactions + risk/compliance reporting, IoT with operational + historical views.

Edge: on Aurora / RDS / Azure SQL, the data needs a pipeline (DMS, Glue, zero-ETL or Fabric mirroring) before analytics sees it. That's a second copy, a second pipeline, a second set of ops. Lakebase keeps it on the lakehouse's storage and governance: synced tables in, Change Data Feed out. Sell it to the CFO as pipeline elimination.

🔁 B. Multi-Copy / Multi-Environment Estates

Enterprises running many copies of the same production database: dev/test/UAT refresh cycles, compliance-testing environments, per-release verification copies. A bank with 20 environment copies pays for 20× compute and storage.

Edge: a branch is O(1) metadata. Every environment becomes a branch, created in seconds, billed only for what diverges, and disposed of freely. Typical candidates: financial services, healthcare, any regulated shop with heavy test-data-management overhead.

💤 C. Long-Tail / Spiky App Portfolios

The "200 small databases" estate: business-hours internal tools, regional apps, batch-driven jobs, seasonal apps. Most of them sit idle most of the day.

Edge: scale-to-zero with a sub-second resume (median <500 ms). Aurora Serverless v2 can pause at 0 ACU too, but it resumes in ~15 s (30 s+ after a day idle), and Azure SQL serverless only auto-pauses after 15+ idle minutes (General Purpose tier). Users don't notice Lakebase waking up. Sell it as portfolio consolidation.

🤖 D. OLTP Apps Adding AI Features

Existing Postgres apps modernizing with AI: copilots, RAG over business data, recommendations, agent features. Suddenly the database needs vectors, agent state and lakehouse grounding next to the OLTP core.

Edge: Lakebase Search + agent memory + lakehouse data on the same platform as the OLTP core. Open-source Postgres (not a fork) means RDS / Aurora PostgreSQL SQL moves largely as-is. Azure SQL (T-SQL) is a rewrite, so target the Postgres pool first.
🚫 Honest no-go zone (don't chase these): steady-state, always-hot classic OLTP with no analytics need (ERP-style, 24/7 full load); workloads that hard-require cross-region DR today; massive write scale-out (Aurora Limitless / DSQL territory); MySQL or T-SQL lift-and-shift; heavy dependence on engine-specific features. Spending cycles here loses deals and credibility. Qualify with one question: "does this app's data also need to be analyzed, copied, or made smarter?" If yes, it's segment A/B/C/D. If no, walk away.

2Activation Play: The Natural Path Past $5K/mo

How it bills: compute per CU-hour while running (1 CU ≈ 2 GB RAM) plus storage per GB-month, with no I/O meter. Scale-to-zero stops compute billing on idle databases (computes ≤ 32 CU, non-HA). HA and always-on production run 24×7, and that's where steady spend comes from. Rates vary by cloud and tier, so size deals in the pricing calculator.

🎯 Three battlegrounds

  • AI agents: memory + state + search in one governed Postgres, the lakehouse-native home for agent data
  • Lakehouse data serving: synced tables + the Data API. No pipeline and no serving copy: the number that moves the CFO
  • Dev/CI branching: hours become seconds. The easiest PoC wow moment

❌ Objection quick answers

  • "Is it faster?" → Don't claim it. The 5× is against our own old engine, and your bottleneck isn't TPS.
  • "Too new" → GA on AWS and Azure, a public SLA, PCI-DSS + HITRUST, and 10M+ databases a day on the engine. Branch a copy and try it for a week.
  • "Aurora scales to zero too" → Yes, since 2024, in ~15 s. Lakebase does it in under half a second, and branches in seconds.
  • "DR not at parity" → True today. Which workloads really need cross-region RPO≈0? For most, HA across AZs + 2–30-day point-in-time restore is enough.
  • "We don't want to migrate" → Don't, yet. Land new apps and agents first.
  • "We're in Hong Kong" → Azure East Asia (HK) is live. On AWS use Singapore or Tokyo; there's no AWS HK region yet.
