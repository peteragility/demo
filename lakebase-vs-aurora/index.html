Lakebase vs Aurora Serverless v2

Pure technical deep dive ｜ fact-checked 2026-09-23 · VLDB paper 09-04 · release notes 09-20 · EN · sales material moved to lakebase-sales-play
⚠️ AWS renamed "Aurora Serverless v2" to Aurora serverless in April 2026 (no action required). This page still says "Aurora Serverless v2" where the source material does.
🧭 One-line summary: Two databases that both believe "log is the database" — separated by where the page of truth lives. Aurora (Gen 2): private quorum storage, single cloud. Lakebase (Gen 3): open-format object storage, any engine reads. Every difference below follows from that single architectural choice.

3Scaling, Cold Start & Cache Hierarchy

Aurora — in-place ramp
  • 0–256 ACU, scales in place. April 2026 platform version 4: up to 45% faster scaling (0.5→256 ACU in ~22 min, was ~40 min); Aug 2026: scale-up events now reach up to 12 ACU within a second before continuing to 256
  • Scale-down deliberately slow (minutes) to prevent thrash
  • max_connections tracks ACU (2 ACU ≈ 135 conns); during ramp windows the ceiling is stale → RDS Proxy + retries needed
  • Resume from auto-pause: ~15s (30s+ if paused >24h — "deep sleep") (status still shows "available" while resuming — PG 13.15+)
Lakebase — compute swap
  • 0.5–64 CU autoscale (max−min ≤ 16 CU spread), fixed 65–112 CU; seconds: new compute attaches to the WAL stream; storage never moves
  • True scale-to-zero: configurable idle timeout, default 24h (60s–7 days range); only for computes ≤32 CU; not available with HA
  • Built-in PgBouncer pooled endpoint (transaction mode)
  • Resume: boot a thin compute, pages lazy-stream from pageserver/object store
⚡ Cold-start race (first connection after scale-to-zero):

~300–500ms (median <500ms, per VLDB paper §5.3)

~30x median gap (500ms vs ~15s; Aurora can hit 30s+ after a >24h pause). Caveat: after either resume the buffer cache is cold — there is no free resume; Lakebase just makes re-reads cheap (next tier is warm) and fast.

Aurora — 2-tier cache, tied to instance life
  • Buffer pool (ACU memory) → quorum storage (pages resident)
  • Scale-up: cache retained, new memory cold · Scale-down: eviction, hot pages can be lost
  • Auto-pause resume: entire cache cold + ~15s boot
Lakebase — 4-tier waterfall, disposable compute
  • RAM → local NVMe → pageserver → object store
  • NVMe survives scale events; pageserver stays warm across compute swaps
  • Cold start: RAM empty but lower tiers warm → pages stream back and re-warm automatically; failover works the same way (new compute attaches to WAL stream)

4Branching — the O(1) Primitive (VLDB 2026, on record)

Mechanics (paper, §4.2)
  • Branch = fork the database history at a branch LSN; parent and child share all physical storage up to that LSN and diverge after
  • O(1) metadata operation — writes a single remote file recording the new timeline identifiers; no physical data copy
  • Branch restore = attach the compute primary to a previous timeline
