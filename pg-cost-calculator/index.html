Reference scenarios 📊

Scenario A — small production app (8 CU ≈ 4 vCPU/16 GB, 200 GB, HA, low I/O)

Lakebase (8 CU floor, Always-On) ≈ $170–230 + storage $69 ≈ $240–300 · Aurora r7g.large I/O-Opt ≈ $190 + $45 = $235 · Aurora Standard + light I/O ≈ $235 · RDS r7g.large multi-AZ ≈ $465 · Azure D4ds HA ≈ $520 + storage · Cloud SQL HA 4/15 ≈ $590 + storage. Read: at small scale, Lakebase's scale-to-zero/Always-On and Aurora I/O-Optimized trade the lead; the legacy-cloud HA tax (×2 instance) is what hurts.

Scenario B — chatty OLTP (8 vCPU/32–64 GB, 500 GB, HA, 2B I/O/mo)

Aurora Standard: I/O alone = $400/mo on top of ~$840 compute → I/O-Optimized wins despite +30% instance price. Lakebase: I/O included; cost scales with CU-hours actually consumed. RDS with provisioned IOPS to cover 2B/mo needs ~10K IOPS ≈ $650/mo of IOPS alone. Read: this is the workload where per-I/O billing models bleed.

Scenario C — dev/test (2 vCPU, 50 GB, no HA, 8h/day weekdays)

Lakebase scale-to-zero: compute only for hours used ≈ $15–30/mo. Aurora/RDS stopped instances still bill storage (~$6/mo) but compute ≈ $0 when fully stopped (Aurora can't stop with replicas; RDS can stop ≤7 days at a time). Cloud SQL storage-only ≈ $8.50/mo when stopped. Read: scale-to-zero is Lakebase's cleanest win.

Billing gotchas each vendor hopes you miss ⚠️

VendorGotcha
LakebaseDefault project autoscaling starts at 8–16 CU — a small app left on defaults pays for capacity it never uses. Scale-to-zero kicks in after 24h of inactivity (not instantly). HA standby ≠ read capacity: it's a sync hot standby for failover — using it for reads risks query cancellations and slows failover; add read replicas instead (up to 6 per branch, zero extra storage, each bills its own CU-hours). Public egress: Neon heritage bills transfer (500 GB/mo included, then ~$0.10/GB) — verify your plan's terms.
AuroraStandard's $0.20/1M I/O quietly wrecks chatty budgets (2B I/O = $400). I/O-Optimized costs +~30% instance but removes it — crossover is typically a few hundred million I/Os/mo. Global Database cross-region replicated write I/O bills even on I/O-Optimized.
RDSgp3 includes only 3,000 IOPS; provisioning to match Aurora-class throughput is where the bill explodes. Multi-AZ = ×2 compute. Stop is capped at 7 days per action.
Azure FlexibleZone-redundant HA = ×2 compute (standby is a live instance). Same-zone HA is cheaper but shares the zone. Storage and IOPS scale independently and both bill.
Cloud SQLHA = ×2 compute AND ×2 storage ($0.17 → $0.34/GB). CPU+memory are billed as separate meters (vCPU $0.0413 + mem $0.007/GiB-hr) — a memory-heavy small-vCPU box surprises.

Model notes & honest caveats 📝

  • This is a list-price model — it excludes egress, backup overages, cross-region replication, support-plan effects, and discount instruments (RIs/CUD/savings plans) except where noted. Real bills also include VAT.
  • Lakebase models CU-hours consumed (profile × size × hours) at $0.111 standard / $0.083 Always-On baseline; storage at $0.345/GB-mo. Your autoscaling telemetry will differ from any static profile.
  • Same-size ≠ same-speed. A CU is not a vCPU is not an ACU. Per the independent pgbench pass (Diggibyte, 2026): Lakebase 1,737 TPS @104ms vs Aurora 1,508 @119ms at a 4M-row/180-client shape — and same-AZ placement doubled Lakebase TPS. Performance-normalize before trusting a raw $ comparison.
  • HA definitions differ. Lakebase: sync standby, RPO 0, automatic failover (kills connections). Aurora: storage-level replication is free; readers bill as instances. Azure: ×2 compute. Cloud SQL: ×2 compute + ×2 storage. RDS: ×2 compute.
  • Azure PAYG rates vary by region and machine generation (Ddsv4/Ddsv5/Dads v5); the $259.88 D4ds v5 figure is East-US-class. Cloud SQL rates are us-central1 Enterprise dedicated.
  • Prices move. Verify in each console (AWS Pricing Calculator, Azure Pricing Calculator, Google Cloud SQL pricing, Databricks Lakebase pricing page) before procurement. Fact-checked against public pages 2026-10-08.
