The isolation ladder 🪜

These five categories describe where the execution boundary sits. A separate kernel reduces shared-kernel exposure, but the tier alone does not rank overall security: granted files, network access, credentials and host callbacks still matter. Some products support several runtimes.

Tier 1 Hardware microVM — dedicated kernel per sandbox (Firecracker, Kata, Hypervisor.framework) ↓ Tier 2 User-space kernel interception — gVisor (syscall filtering, shared real kernel) ↓ Tier 3 Interpreter-level sandbox — language VM, code never sees the OS (Monty) ↓ Tier 4 Shared-kernel containers — Docker (host-kernel exposure remains) ↓ Tier 5 OS policies — Seatbelt / Landlock restrictions on a host process

Coding-agent boundaries vary by operating system and configuration. A guest-kernel exploit inside a VM still needs to cross the VM boundary to reach the host; credentials and allowed data paths require separate controls.

Databricks Sandbox: isolation + governance 🟠

Scope data access for the integration you actually use

Agent Bricks sandbox tool: configure --scope for tables, volumes or workspace folders, and opt into writes explicitly. It runs with the requesting user's permissions by default; --auth app uses the app service principal. Official quickstart ↗

SDK and CLI: each sandbox receives a credential for its creator in the DEFAULT profile of ~/.databrickscfg, used automatically by the SDK and CLI. Tokens last one hour and refresh automatically for up to 24 hours, independently of the creator's sign-in session; signing out does not revoke this access. Do not assume agent-tool scopes apply to arbitrary sandbox code. Current Beta egress is unrestricted and cannot be configured; default ingress is closed and cannot be changed, and public IP addresses can change. Credentials and networking ↗

Default quotas: 200 active sandboxes per user (800 across all states) and 400 active per workspace (2,000 total). Request increases through your Databricks account team.

Plus Lakebase instant branching: agents can test writes in an isolated copy-on-write branch. Validation and promotion are separate: use migrations for schema changes and explicit application logic to apply approved business writes; branches do not merge natively. Lakebase branch behavior and billing ↗

The public overview describes an isolated environment without specifying a dedicated kernel or hypervisor. Confirm that boundary for your threat model. Access to governed data and outbound connectivity remain separate considerations.

Four design philosophies 🧭

These approaches address different parts of the security boundary:

1. Start open, then restrict 🔓

Codex · Gemini CLI · Claude Code

Full environment first, then whittle down — network rules, filesystem rules, syscall filters. Cursor's sandboxing writeup documents how painful this is across platforms. Every vendor in this camp has a published 2026 escape.

2. Hardware isolation by default 🧱

E2B · Docker Sandboxes · AgentCore microVM sessions

A dedicated guest kernel adds a boundary around untrusted code. Hypervisor security, runtime configuration, credentials and data access still need review.

3. Deny-by-default interpreter 🐍

Monty · Strands Box (Python layer)

The interpreter exposes only supported operations and granted host capabilities. Audit callbacks and mounted resources; check Python and package compatibility. Philosophically closest to "firewall that blocks everything, then allowlists".

4. Governance-native 🏛️

Databricks Sandbox (+ Unity AI Gateway)

Use explicit resource scopes and a deliberate user or app identity for the Agent Bricks sandbox tool. Verify data permissions and audit coverage for the actual query path.

The Novee lesson 🚨

October 2026 agent-sandbox audit (disclosed with Anthropic, Google, OpenAI)

  • Claude Code: 2 CVEs (CVE-2026-54316, CVE-2026-45786)
  • Gemini CLI: CVSS 10 chain — one public issue → credential compromise → push to main on a project with ~2M monthly installs
  • Codex: 2 independent sandbox-escape paths
  • The headline: "Credentials escaped in every architecture, including from a Codex sandbox with TCP, UDP and DNS fully disabled."

Conclusion: the isolation tier protects the host from the code. It does nothing for the secret the code legitimately needs. 2026's lesson: isolation is table stakes — credential architecture is the real differentiator (stand-in values, gateway injection, downscoped tokens).

The 2027 standard answer 🧩

The strongest stack combines all three lessons: microVM hard isolation (E2B / Databricks / AgentCore) + downscoped or injected credentials (UC downscoping / gateway stand-ins) + deny-by-default interpreter for generated code (Monty). Any one alone leaves a published 2026 gap.
