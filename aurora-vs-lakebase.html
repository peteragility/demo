🏛️ Architecture Overview

Amazon Aurora
Cloud-native OLTP · MySQL/PostgreSQL compatible · GA 2014
┌─────────────────────────────────┐ │ Compute Layer (stateless) │ │ Primary + up to 15 Read Reps │ └──────────┬──────────────────────┘ │ (log records only) ┌──────────▼──────────────────────┐ │ Distributed Storage Layer │ │ 6 copies across 3 AZs │ │ Auto-scaling 10GB → 128TB │ └─────────────────────────────────┘

Core innovations

  • Compute / Storage separation — compute only ships redo log records to storage
  • Quorum writes — 6 copies, 4/6 write quorum, 3/6 read quorum
  • Self-healing storage via peer gossip + parallel re-replication
  • No log replay on crash — storage layer handles redo asynchronously
Databricks Lakebase
Postgres-on-Lakehouse · Built on Neon · GA late 2025
┌─────────────────────────────────┐ │ Postgres Compute (Neon-based) │ │ Serverless · branching │ └──────────┬──────────────────────┘ │ (WAL stream) ┌──────────▼──────────────────────┐ │ Object Storage (S3/ADLS/GCS) │ │ Delta Lake format │ │ Unity Catalog governance │ └─────────────────────────────────┘

Core innovations

  • Acquired Neon May 2025 (~$1B) — Postgres serverless engine
  • Storage-compute separation via object storage (not block)
  • Bidirectional Delta sync — OLTP data instantly available for analytics
  • Git-like branching — copy-on-write Postgres branches
  • Unity Catalog unifies governance for OLTP + OLAP

🎯 Use Case Positioning

Aurora strengths
  • Pure OLTP workloads (e-commerce, SaaS, finance)
  • Extreme write throughput + low latency
  • AWS ecosystem (Lambda, API Gateway, etc.)
  • Mature production workloads
  • Multi-region active-active (Global Database)
Lakebase strengths
  • HTAP scenarios — same data for transactions + analytics, no ETL
  • AI/ML — feature store + serving from same DB
  • Tight OLTP + lakehouse integration
  • Postgres branching for dev/test/agents
  • Existing Databricks customers simplifying stack

💡 Architectural Philosophy

Aurora — "Best-in-class OLTP, integrate with analytics via pipelines."
Focus on doing OLTP perfectly. Analytics arrives via Zero-ETL → Redshift / S3 → Athena. Two systems, data movement between them.
Lakebase — "One platform, OLTP + analytics on the same data."
Break the OLTP / OLAP silo. Operational data is instantly queryable from the lakehouse. Postgres protocol on the wire, lakehouse architecture underneath.

🔬 Neon Architecture Deep Dive

Traditional Postgres runs as one stateful box — compute + storage tightly coupled on one filesystem. Neon (acquired by Databricks May 2025, $1B) splits the two layers and connects them only via the WAL (Write-Ahead Log) stream.

┌──────────────────────────────────────────────────┐ │ COMPUTE LAYER (Ephemeral, Stateless) │ │ ┌─────────────────────────────────────────┐ │ │ │ Postgres process │ │ │ │ • Parse / Plan / Execute │ │ │ │ • Buffer cache (RAM) │ │ │ │ • Local NVMe cache (hot pages) │ │ │ │ • NO local data files (!) │ │ │ └─────────────────────────────────────────┘ │ └────────────┬───────────────────┬─────────────────┘ │ │ WAL stream out Page reads in │ │ ┌────────────▼───────────────────▼─────────────────┐ │ DURABLE STORAGE LAYER (Disaggregated) │ │ │ │ ┌──────────────┐ ┌────────────────────────┐ │ │ │ Safekeepers │───▶│ Pageservers │ │ │ │ (Paxos) │ │ (LSM-tree on local │ │ │ │ • WAL only │ │ NVMe + S3 tiering) │ │ │ │ • 3-way repl │ │ • Materialize pages │ │ │ │ • Quorum ack │ │ on demand from WAL │ │ │ │ = COMMIT │ │ • Cache hot pages │ │ │ └──────────────┘ └─────────┬──────────────┘ │ │ │ │ │ ▼ │ │ ┌────────────────────────┐ │ │ │ Object Storage (S3) │ │ │ │ • Cold pages │ │ │ │ • Long-term history │ │ │ │ • Snapshots │ │ │ └────────────────────────┘ │ └──────────────────────────────────────────────────┘

🔑 The Three Storage Components

1. Safekeepers — Durability

  • Receive the WAL stream from compute
  • Paxos quorum: 3 safekeepers, 2/3 acknowledge → commit
  • Forward WAL to Pageservers
  • Commit latency = quorum WAL ack time (millisecond range)

2. Pageservers — Page reconstruction

  • Rebuild Postgres 8KB pages from WAL deltas
  • LSM-tree on local NVMe (RocksDB-style)
  • On page request: find latest materialized image + replay WAL deltas on top
  • Tier cold pages out to S3

3. Object Storage — S3 / ADLS / GCS

  • Long-term durability
  • Not on the critical path — query latency is independent of S3
  • Snapshots, time travel, branch base layers

⚡ Key Architectural Wins

A. Image Generation Pushdown 2026 Q1

Traditional Postgres protects against torn pages (OS crash mid-page-write) by embedding Full Page Writes (FPW) in WAL — first modification of any page writes the entire 8KB to WAL. Massive write amplification.

Lakebase fix:

  • Compute is stateless → no local page, no torn-page risk
  • Disable FPW → WAL volume drops dramatically
  • Reads need long delta replay? → Pageserver itself emits periodic page images as reset points
  • Result: ~5× faster Postgres writes (Databricks blog)

B. Instant Branching (storage-layer copy-on-write)

  • A branch = new compute + a logical pointer into existing storage
  • Branch creation: ~1.5 seconds (vs RDS clone in minutes)
  • Stores only diff, no data duplication
  • True git-like semantics for databases

C. Scale-to-Zero

  • Idle compute → suspended
  • Resume in ~hundreds of ms (cold start)
  • Storage continues handling WAL (which is empty when idle) → real cost savings

D. Zero-Downtime Patching (Prewarming)

  • Stateless compute → spin a new replica, prewarm buffer cache, then failover
  • Eliminates traditional Postgres upgrade downtime

🤖 AI / Agentic Workload Fit

Databricks explicitly positions Lakebase as "the operational database for AI agents and apps." This is where it gets genuinely interesting.

🎯 Why Postgres for Agents?

Agentic AI demands an unusual mix of database capabilities:

  • High write volume — agent state, tool calls, traces
  • Vector search — RAG, semantic memory
  • Strong consistency — don't lose tasks, payments, side effects
  • Low-latency reads — feature serving, sub-10ms
  • Ephemeral environments — agents that spin up DBs and throw them away
  • Audit trail — governance and compliance
No traditional database stack covers all of these. Lakebase's combination — Postgres + pgvector + scale-to-zero + branching + Unity Catalog + Delta sync — is the specific bundle agents need.

⚙️ 5 Core Patterns Lakebase Enables

1. Feature Serving for Inference (sub-10ms)

  • Online feature store inside Postgres (hot features in RAM/NVMe cache)
  • Synced tables auto-materialize Delta features → Lakebase
  • No Redis / DynamoDB middle layer required
  • pgvector for embeddings + similarity search
  • True single-digit-ms feature lookup

2. Agent Memory & State (Durable, Transactional)

-- Agent conversation history
CREATE TABLE agent_sessions (
  session_id   UUID PRIMARY KEY,
  user_id      TEXT,
  started_at   TIMESTAMPTZ,
  state        JSONB,
  embedding    VECTOR(1536)   -- pgvector
);
  • ACID transactions for tool-call atomicity
  • JSONB for flexible state schemas
  • pgvector for semantic memory recall
  • Directly queryable from Databricks SQL / dashboards

3. Ephemeral Sandboxes per Agent Task KILLER

Pattern from Syren's pricing agent example:

# 1. Agent generates UPDATE statement (LLM, 0.5-1.5s)
sql = llm.generate_sql(user_intent, schema)

# 2. Spin up Lakebase branch (~1.5s, copy-on-write)
branch = lakebase.create_branch(parent="prod")

# 3. Run on branch — production untouched
branch.execute(sql)

# 4. Run impact analysis / model inference on branch data
impact = model_serving.predict(branch.query("SELECT ..."))

# 5. Show user → if approved, atomic commit to prod
if user_approves:
    branch.merge_to("prod")   # atomic
else:
    branch.delete()           # zero-cost rollback

Why it matters: agents can rehearse destructive operations safely. Without branching, an agent writing to prod = potential disaster.

4. RAG with Operational Data

  • Operational tables auto-sync to Delta (governed by Unity Catalog)
  • Reverse: Delta features sync back to Lakebase for hot serving
  • One source of truth — agent answers and dashboards stay consistent
  • pgvector handles embedding search (no separate Pinecone / Weaviate)

5. Multi-Tenant Agent Platforms — "Databases as Cattle"

  • Spin a database per user / per agent / per task via API
  • Cost approaches zero (scale-to-zero + shared storage)
  • Versioning: every agent action = checkpoint, rollback = single API call
  • Impossible on traditional Postgres — each instance is a GB-scale cost

🎯 Strategic Take for the Databricks Role

Lakebase is the final piece of the Databricks "Data + AI Platform" story:

Before: Databricks = lakehouse for analytics + ML training. Customers still need a separate OLTP DB (Aurora / Postgres) for apps.

After: Databricks = one platform for OLTP + OLAP + ML training + ML serving + AI agents. Aurora becomes commodity infrastructure; Lakebase sits higher in the customer's AI value chain.

Talking points for HK / TW SA team

  • Customers building AI agents → Lakebase is a natural fit (vs stitching Aurora + pgvector + Redis + Snowflake)
  • Customers fed up with two-tier data architecture pain → sell simplification directly
  • Postgres compatibility → clean migration path, not a new SQL dialect lock-in
  • Branching = killer demo for dev/test workflows

Competitive lens

  • vs Aurora + Bedrock — Lakebase + Mosaic AI is true vertical integration
  • vs Snowflake Hybrid Tables / Unistore — Snowflake remains weak on OLTP latency and branching
  • vs Oracle 23ai — Oracle has vector + JSON but proprietary; Lakebase wins developer mindshare on open Postgres
