Amazon Aurora vs Databricks Lakebase

Both split compute from storage. They disagree on where the page of truth lives, and that one choice decides branching, cold starts, openness and what AI agents can do with the database.

Peter Chan · Field Engineering, HK + TW · v2 (first edition 12 May 2026)
Companions: Lakebase vs Aurora: the numbers · Lakebase Sales Play · Why LTAP changes everything

🧭 The one-line difference

Aurora keeps pages in private quorum block storage that only Aurora can read. Lakebase keeps Postgres pages + WAL in cloud object storage and wires them to the lakehouse: Delta in through synced tables, changes out through Change Data Feed.

🟧 Where Aurora wins

10+ years in production · cross-region DR (Global Database, up to 10 regions) · 15 replicas · 256 TiB · scale-out writes (Limitless, DSQL) · MySQL.

🟥 Where Lakebase wins

<500 ms median cold start (Aurora: ~15 s) · O(1) branching · open-source Postgres 16–18, not a fork · Unity Catalog + lakehouse sync · vector + BM25 search inside the database.

⚠️ What not to argue

Raw TPS. The "5× faster writes" headline is Lakebase vs its own previous write path, and Aurora never paid that tax. Pick on architecture fit, not benchmarks.

What changed since the May edition (every number re-verified 28 Sep 2026)
  • Lakebase is GA: AWS 22 Jan 2026, Azure 2 Mar 2026, with a public SLA since July (99.99% with HA · 99.9% single compute). The May page said "GA late 2025".
  • Aurora grew too: the storage ceiling is now 256 TiB (not 128), Aurora PostgreSQL ships PG 18, and Serverless v2 has scaled to 0 ACU since Nov 2024. It resumes in about 15 s.
  • Global Database is not active-active. It has one writer region and up to 10 read-only regions. AWS's active-active answer is Aurora DSQL.
  • Lakebase doesn't store Delta. It stores Postgres pages + WAL. Delta arrives through Change Data Feed (Public Preview, ~15 s).
  • Branches don't merge back. The agent-sandbox pattern below is corrected: rehearse on a branch, then replay the vetted change on production.
  • New since May: HA with 1–3 secondaries, up to 6 read replicas, 64 CU autoscaling, Postgres 18, Lakebase Search GA (18 Sep), PCI-DSS + HITRUST on AWS.

🏛️ Architecture Overview

Amazon Aurora
Cloud-native OLTP · PostgreSQL / MySQL-compatible · GA 2014
┌─────────────────────────────────┐ │ Compute: writer + ≤15 readers │ │ provisioned or Serverless v2 │ └──────────┬──────────────────────┘ │ redo log records only ┌──────────▼──────────────────────┐ │ Quorum block storage (private) │ │ 6 copies × 3 AZs · 4/6 writes │ │ grows to 256 TiB │ └─────────────────────────────────┘

Core innovations

  • "The log is the database": compute ships only redo records, and storage materializes the pages
  • Quorum writes: 6 copies, 4/6 write quorum, 3/6 read quorum
  • Self-healing storage via peer gossip + parallel re-replication
  • No log replay on crash: storage applies redo asynchronously
  • Scale-out options: Global Database (reads + DR), Limitless (sharded PG), DSQL (active-active)
Databricks Lakebase
Serverless Postgres on lake storage · Neon architecture · GA 2026
┌─────────────────────────────────┐ │ Stateless Postgres compute │ │ 0.5–112 CU · scale to zero │ └──────────┬──────────────────────┘ │ WAL stream only ┌──────────▼──────────────────────┐ │ Safekeepers → Pageservers │ │ object storage (S3 / ADLS) │ │ Postgres pages + WAL history │ └──────────┬──────────────────────┘ │ synced tables ⇄ CDF ┌──────────▼──────────────────────┐ │ Lakehouse · Delta · Unity Cat. │ └─────────────────────────────────┘

Core innovations

  • Neon engine: acquisition announced 14 May 2025 (reported ~$1B)
  • Compute is cattle: storage never moves, so resume, resize and failover just attach a new compute (median cold start <500 ms)
  • Git-like branching + point-in-time restore from the page-history chain (2–30-day window)
  • Lakehouse on both sides: Delta → Postgres synced tables; Postgres → Delta Change Data Feed (Public Preview)
  • Unity Catalog governance · open-source Postgres 16 / 17 / 18

🎯 Use Case Positioning

Aurora strengths (say these first)
  • Steady, always-hot OLTP at very large scale (256 TiB, 15 replicas)
  • Cross-region DR and global reads (Global Database, up to 10 regions)
  • Scale-out writes: Limitless (sharded) or DSQL (active-active, 99.999% multi-region)
  • MySQL estates and deep AWS-native wiring (IAM, RDS Proxy, Lambda)
  • Change-averse production that values a 10-year track record
Lakebase strengths
  • Apps on lakehouse data: synced tables turn curated Delta into millisecond reads
  • Agent memory, state and search (pgvector + Lakebase Search) in one governed Postgres
  • Fleets of small or spiky databases (per tenant, per agent, dev/test) with sub-second resume
  • Branch-per-PR / per-agent sandboxes, and PITR as a branch
  • Databricks customers consolidating governance in Unity Catalog
The one-question qualifier: does this app's data also need to be analyzed, copied (dev/test, branches) or made smarter (AI)? If yes, it's Lakebase territory. If it's always-hot 24×7 OLTP with a hard cross-region RPO requirement and no analytics need, respect Aurora.

💡 Architectural Philosophy

Aurora: "Best-in-class OLTP; feed analytics through pipelines."
Pages of truth live in storage that only Aurora's engine can read. Analytics gets a copy, via zero-ETL into Redshift or a SageMaker lakehouse. Two systems, with managed data movement between them.
Lakebase: "The database is a view over lake storage."
Pages and WAL live in cheap, durable object storage; compute is a disposable cache. The lakehouse sits on both sides, with Delta in (synced tables) and changes out (Change Data Feed), under one Unity Catalog.
The research framing. Databricks' VLDB 2026 paper classes Aurora, Socrates and AlloyDB as second-generation systems: storage separated internally, but formats proprietary and access single-engine, which it calls "a transitional architecture." Lakebase is presented as the third generation: transactional systems rebuilt natively for object storage, elastic compute and AI-era workloads.
Where it's heading: LTAP. Announced at Data + AI Summit (June 2026), LTAP unifies OLTP and OLAP at the storage layer instead of forcing one engine to do both jobs. The first pieces are in Beta: LTAP Direct Writes loads synced tables straight into Lakebase storage, and Lakehouse Real-Time serves low-latency SQL on lake tables. Sell the direction; scope deals on what's GA. (LTAP explainer)

🔬 Inside Lakebase (Neon architecture)

Traditional Postgres runs as one stateful box, with compute and storage tightly coupled on one filesystem. The Neon architecture behind Lakebase splits the two and connects them only through the WAL (write-ahead log) stream.

🔑 The Three Storage Components

1. Safekeepers: durability

  • Receive the WAL stream from compute
  • Paxos quorum: 3 safekeepers across AZs, 2 of 3 acknowledge = commit
  • Forward WAL to the pageservers
  • Commit latency = quorum WAL ack time (low milliseconds, cross-AZ)

2. Pageservers: page reconstruction

  • Rebuild Postgres 8 KB pages from WAL deltas (a GetPage@LSN call)
  • Store image layers + delta layers in an LSM-tree-like structure on local NVMe
  • On request: find the latest page image before the LSN, replay the deltas on top, return the page
  • Tier cold layers out to object storage

3. Object storage: S3 / ADLS

  • Long-term durability at object-storage prices
  • Off the commit path: reads touch it only on a cache miss for cold layers
  • History that powers branching, point-in-time restore and snapshots

⚡ Key Architectural Wins

A. Image Generation Pushdown May 2026

Stock Postgres protects against torn pages (an OS crash mid-page-write) by embedding full-page writes (FPW) in the WAL: the first change to any page after a checkpoint writes the whole 8 KB page to WAL. That's massive write amplification.

Lakebase fix:

  • Compute is stateless, so there's no local page and no torn-page risk
  • Turn FPW off, and WAL volume drops dramatically
  • Long delta chains on read? The pageserver emits page images itself as reset points
  • Result: up to 5× write throughput (4.5× on 32 vCPU), −94% WAL, 2× lower read tail latency (Databricks engineering blog)

Read it right: this is Lakebase against its own previous write path. Aurora's storage never needed full-page writes, so this closes a gap rather than opening one against Aurora.

B. Instant Branching (storage-layer copy-on-write)

  • A branch = a fork of the database history at an LSN; parent and child share every page up to that point
  • Created in seconds regardless of size (an Aurora clone is a new cluster to provision)
  • Stores only the diff; up to 500 branches per project, with optional TTL expiry
  • Production telemetry shows some databases more than 500 branches deep (VLDB 2026)

C. Scale-to-Zero

  • Idle compute suspends after a timeout you choose (60 s – 7 days; default 24 h)
  • <500 ms median cold start, from a pool of warm VMs (VLDB 2026 §5.3)
  • Suspended = zero compute cost; the lower cache tiers stay warm, so pages stream back fast
  • Limits: computes ≤ 32 CU, and not with HA; production branches can stay always-on

D. Fast Failover and Resize

  • HA runs 1–3 secondaries in other AZs; on failure one is promoted and the app continues from the last committed transaction
  • The primary connection string follows the new primary automatically
  • Resizing or replacing compute never moves data: a new compute simply attaches to the same storage

🤖 AI / Agentic Workload Fit

Databricks positions Lakebase as the operational database for AI agents and apps, and the telemetry backs the bet. Per the VLDB 2026 paper, Lakebase creates and manages more than 10 million databases a day, and AI agents now create roughly 4× more of them than humans.

🎯 Why Postgres for Agents?

Agentic AI demands an unusual mix of database capabilities:

  • High write volume: agent state, tool calls, traces
  • Search: semantic (vector) and exact-term (keyword) recall over memory
  • Strong consistency: don't lose tasks, payments or side effects
  • Low-latency reads: feature and context serving in single-digit ms
  • Ephemeral environments: agents that spin up databases and throw them away
  • Audit trail: governance and compliance
No traditional stack covers all of these in one place. Lakebase's bundle of Postgres, pgvector + Lakebase Search, scale-to-zero, branching, Unity Catalog and lakehouse sync is the specific set agents need.

⚙️ 5 Core Patterns Lakebase Enables

1. Feature and Context Serving for Inference

  • Synced tables materialize Delta features into Lakebase (continuous mode: seconds of lag)
  • Hot rows stay in RAM / NVMe cache, so point reads return in single-digit milliseconds
  • No Redis or DynamoDB side-copy to build and reconcile
  • The PostgREST-compatible Data API exposes tables over HTTP when the caller isn't a Postgres client

2. Agent Memory & State (durable, transactional)

-- Agent conversation history
CREATE TABLE agent_sessions (
  session_id   UUID PRIMARY KEY,
  user_id      TEXT,
  started_at   TIMESTAMPTZ,
  state        JSONB,
  embedding    VECTOR(1536)   -- pgvector (or lakebase_vector)
);
  • ACID transactions for tool-call atomicity
  • JSONB for flexible state schemas
  • Vector + BM25 hybrid recall with Lakebase Search (GA 18 Sep 2026)
  • Every change can land in Delta through Change Data Feed, for dashboards and evals

3. Ephemeral Sandboxes per Agent Task KILLER

Pattern from Syren's pricing-agent example, with the last step corrected:

# 1. Agent drafts a risky change (LLM, ~1 s)
sql = llm.generate_sql(user_intent, schema)

# 2. Branch production in seconds (copy-on-write, no data copied)
branch = lakebase.create_branch(parent="production", ttl="4h")

# 3. Rehearse on the branch; production untouched
branch.execute(sql)

# 4. Score the impact on the branch's data
impact = model_serving.predict(branch.query("SELECT ..."))

# 5. Branches don't merge back: if approved, replay the vetted SQL on prod
if user_approves(impact):
    prod.execute_in_transaction(sql)
branch.delete()   # zero-cost cleanup either way (or let the TTL expire)

Why it matters: agents can rehearse destructive operations on real data safely. Without branching, an agent writing straight to production is a potential disaster.

4. RAG with Operational Data

  • Change Data Feed lands every insert, update and delete in a Unity Catalog Delta table (~15 s, Public Preview)
  • Synced tables push curated Delta back into Lakebase for hot serving
  • One source of truth, so agent answers and dashboards stay consistent
  • Lakebase Search does vector + keyword retrieval in the same database, with no separate Pinecone or Elastic

5. Multi-Tenant Agent Platforms: "Databases as Cattle"

  • Spin up a database per user, per agent or per task through the API (Postgres APIs GA, Aug 2026)
  • Idle cost approaches zero: scale-to-zero plus shared storage
  • Every agent action can be a checkpoint; rollback is a branch reset or a point-in-time branch
  • Aurora can idle at 0 ACU too, but minutes-long cluster creation and ~15 s resumes make per-task databases impractical

🎯 Strategic Take

Lakebase closes the last gap in the Databricks "Data + AI Platform" story:

Before: Databricks = lakehouse for analytics and ML. Customers still ran a separate OLTP database (Aurora / RDS / Azure SQL) for their apps, plus pipelines to keep the two in sync.

After: Databricks = one platform for OLTP, OLAP, ML training and serving, and AI agents, with the operational database sitting on the same storage and governance as everything else. Aurora stays excellent at being a database; Lakebase aims to be the database of the data platform.

Talking points for the HK / TW team

  • Agent builders: memory + state + search in one governed Postgres, vs stitching Aurora + pgvector + Redis + a search engine
  • Start where the data already is: synced tables turn curated Delta into millisecond APIs. It's the fastest path to production
  • Postgres compatibility: open-source PG 16–18, so RDS / Aurora PostgreSQL apps move with few changes. Plan the cutover, though: no tablespaces, and native logical replication isn't available yet
  • Branching is the demo: a prod-sized branch in seconds, reset in one click
  • Regions: Azure East Asia (Hong Kong), Japan East and Southeast Asia; AWS Singapore, Tokyo, Sydney and Mumbai. There is no AWS Hong Kong region yet

Competitive lens

  • vs Aurora + Bedrock: Lakebase + Agent Bricks keeps data, models and governance on one plane, not three services
  • vs Aurora DSQL: active-active and 99.999% multi-region, but a different job (global writes) on a PostgreSQL-compatible subset. Don't fight it on its turf
  • vs Snowflake Postgres (from the Crunchy Data acquisition, on AWS + Azure): a credible managed Postgres now. Differentiate on serverless architecture (branching, scale-to-zero), lakehouse sync and Unity Catalog
  • vs Azure SQL + Fabric Mirroring / Azure HorizonDB (Preview): Microsoft's OLTP-to-analytics answer is mirroring, a managed copy into OneLake
  • vs Oracle AI Database 26ai: vector + JSON, but proprietary. Lakebase wins developers on open Postgres
  • vs Google AlloyDB: strong columnar engine + AlloyDB AI, but in the VLDB framing it's second-generation: proprietary storage, one engine
