Objection 01

Autoscaling scales in and out — does the buffer cache go cold every time?

Short answer: in-place scaling keeps connections and caches; only scale-to-zero empties them. Understand the four cache layers first:

1Shared buffers — Postgres process, DRAM. Hot working set; nanosecond access.
2LFC (Local File Cache) — compute node, local NVMe. Warm extension of shared buffers; exists because reads bypass the OS page cache entirely — data arrives over the network from the pageserver, not through a local filesystem, so the OS has nothing to cache.
3Pageserver warm tier — storage service, same region, local NVMe. Materialized pages; survives compute restarts and scale-to-zero.
4Object storage — regional object store, cold tier. System of record: base images + WAL deltas.
  • LFC is custom-built, not the OS page cache. It's a plain file deliberately placed so the OS page cache backs it: DRAM available → fully in memory; under pressure → spills to NVMe.
  • In-place scaling does not restart Postgres and does not drop connections. The autoscaler tracks working-set size to protect cache hit rate. Be precise about eviction: yes, both layers can evict during scale-down — DRAM shrinks, so shared buffers give up pages and LFC shrinks too. What scaling improves is which pages get evicted (working-set-aware, not blind) and where misses land afterwards (the NVMe tier absorbs them before the pageserver is touched).
  • On fixed computes ≥80 CU (≥18 on Neon), the old setup was replaced: previously autoscaling computes were capped at ~1 GB shared buffers with LFC taking the rest (up to 75% of DRAM). Now, on those fixed sizes, LFC is disabled entirely and shared buffers = 75% of DRAM with huge pages — an 80 CU compute shows shared_buffers = 120GB. Production results: 2× throughput, storage reads 8K→1.5K/s (5× fewer), one customer's CPU 20→4 cores, cache hit ~100%. Dynamic shared buffers for autoscaling computes are still on the roadmap.
Sizing rule: each CU = 2 GB RAM. Set min CU so its RAM covers the working set — then steady-state reads never leave the machine, regardless of scaling.

The fixed-only threshold: autoscaling exists only up to 64 CU. 65–112 CU computes are fixed-size only — a dedicated, always-on machine with a huge stable shared buffer and zero scaling movement.

Honest caveat: pausing (scale-to-zero) clears layers 1–2 — compute is stateless and its NVMe contents aren't guaranteed to follow rescheduling. Layer 3 survives, so first queries after resume hit in-region NVMe, not cold object storage. Median cold start <500 ms (VLDB §5.3). Production guidance: turn scale-to-zero off — it's unavailable with HA anyway.
Objection 02

LFC vs a regular NVMe cache — and does scale-to-zero clear both?

Why LFC exists: the disaggregated read path bypasses the filesystem entirely — pages arrive over the network from the pageserver — so the OS page cache never sees the data. Postgres needs a cache below shared buffers; nothing provides one; LFC was built. It's a plain file deliberately placed on the filesystem so the OS page cache backs it: DRAM-rich = fully in memory; DRAM-tight = spills to NVMe.

Side benefits: no double buffering — 1 GB of data costs 1 GB of RAM, not 2.

  • Smarter eviction: the OS page cache evicts blind (generic kernel heuristics); LFC evicts based on which pages Postgres is actually re-reading, so the working set survives longer.
  • Resizes with autoscaling, live: the autoscaler adjusts LFC size in step with CU changes while Postgres keeps running. Shared buffers are a static startup parameter — changing them requires a restart. (That's exactly why fixed computes skip LFC and put the whole cache in shared buffers: with a fixed size there's nothing to resize.)

Scale-to-zero clears layers 1–2 (shared buffers + LFC) — the compute is stateless. Layers 3–4 untouched. Resumption: <500 ms median, first queries served from the pageserver warm tier.

Objection 03

Compute/storage separation adds a network hop — throughput suffers at high QPS?

Be precise about where the hop actually is:

  • Working-set reads: no hop. Hits in shared buffers/LFC never touch the network.
  • The separation itself is not exotic. Aurora pioneered the same shape: compute instances over a shared, regional, log-structured storage fleet — and it resolves the hop the same way we do, with a big local cache on the compute so hot reads never cross the network.
  • Commit path: one cross-AZ WAL hop — but every HA database pays this. Aurora's 4/6 quorum and RDS Multi-AZ sync standby are the same class of cost. And yes — Aurora is log-is-the-database too: it also ships redo-log records only (never full pages) to its storage fleet. Lakebase is in the same school: WAL goes to a safekeeper quorum, and there is no second hop beyond the commit ack.

Published numbers (VLDB 2026 · TPROC-C · p95 ≤ 20 ms · equal durability and latency limits):

Write path: full-page-image pushdown (May 2026) → up to 5× write throughput, −94% WAL, 2× lower read tail latency.

Where the honest limits are:

  • Pure cold-read-heavy workloads (random scans far larger than any cache) still pay the pageserver round trip. A pure local-NVMe box wins that specific benchmark — don't fight it.
  • One writer per branch. Beyond ~112 CU single-node, or write sharding across nodes, the right products are Aurora Limitless / DSQL. Qualify out early — it buys credibility elsewhere.
High-throughput guidance: for sustained high-transaction QPS, run fixed mode — full 75%-of-DRAM shared buffers, huge pages, zero scaling movement. That is the configuration the published numbers are measured on.
Objection 04

What about write throughput? Reads are cached — but what happens when my workload is write-heavy?

The write path is where separated storage usually bleeds, so it gets its own engineering:

  • WAL-only commit path — the compute never ships full pages; safekeeper quorum acks the log, page materialization happens in the storage tier in the background.
  • Full-page-image pushdown (May 2026) — the most expensive part of Postgres writing (full-page images into WAL after checkpoints) is moved out of the compute's critical path into storage. Published results: up to 5× write throughput, −94% WAL volume, 2× lower read tail latency.
  • No I/O charges — write-heavy workloads on Aurora/RDS pay per request; Lakebase storage is flat-rate, so bursty write days don't become a bill surprise.

  • Commit latency includes the cross-AZ safekeeper ack — bounded, but present. Sub-millisecond commit-ack workloads at extreme QPS should benchmark their own path (offer a POC on a branch of their data).
  • For sustained high write QPS: run fixed mode — that is the configuration these numbers are measured on.
Objection 05

Are pageservers shared? Is my data exposed? Do I need to set up CMK myself?

Compute: each project's Postgres runs in its own microVM (NeonVM — QEMU/KVM). Not shared processes — the buffer cache in your VM is physically unreachable by other tenants.

Storage (safekeepers + pageservers): multi-tenant shared infrastructure, deployed regionally — like every cloud database's storage fleet, Aurora included. Tenancy is logical: one storage tenant per project, one compute per tenant/timeline, isolated timelines (VLDB §3.5). Encryption everywhere; pageserver access requires the tenant's timeline credentials.

CMK — default is system-managed; CMK is opt-in:

  • Out of the box: platform-managed encryption keys. No action needed.
  • Compliance requires it? Bring your own. Property that matters: revoking the key revokes all access to the data — the control point auditors care about.
  • Private Link / private connectivity supported.

Attestations: SOC 2 Type 2 · PCI-DSS · HITRUST (all AWS regions) · HIPAA, C5, TISAX via compliance security profile.

Honest boundary: if a customer mandates physically single-tenant hardware, no managed serverless database qualifies — Lakebase included. Qualify out.
Objection 06

Connection pooling — built-in or build it ourselves? When pooled vs not?

Built-in: Lakebase runs PgBouncer for you. Clients connect to the -pooler endpoint hostname; up to 10,000 concurrent client connections share a smaller server pool. Each server connection is held for one transaction, then returned.

pool_mode = transaction
max_client_conn = 10000
default_pool_size = 0.9 × max_connections
max_prepared_statements = 1000
query_wait_timeout = 120

Fixed configuration — not customizable.

Use pooled mode when: many short-lived connections (serverless functions, web APIs, ORMs opening per-request connections); client count above max_connections; no reliance on session-level state.

Connect directly (no -pooler) when: you need session SET, session advisory locks, LISTEN/NOTIFY, cursors held across transactions, or per-client temp tables; long-lived sessions needing guaranteed backend identity; or OAuth-role authentication (pooling supports native password only).

What the app side must do (both modes): connection timeouts, retry-on-error with backoff, never hold transactions open across user think-time. If scale-to-zero is enabled, connection retry logic is mandatory — suspending drops all connections; reactivation <500 ms but the TCP connections are gone.

Connection-breakage matrix:

EventConnections
Autoscaling within min/max rangeNot interrupted — in-place, no restart
Changing min/max CU configurationPossible brief interruption (one-off)
Scale-to-zero suspensionAll dropped; reactivation <500 ms; app retry required
HA failoverResumes from last committed transaction; pooler absorbs most of it
Rule of thumb: production = scale-to-zero off → the only connection-breaking events are deliberate config changes and failovers.
Objection 07

My workload is stable — I want provisioned and dedicated. Is Lakebase only for test/bursty?

No. "Serverless is how Lakebase can run, not how it must run."

  • Choose fixed size (0.5–64 CU, or fixed-only 65–112 CU), disable scale-to-zero, add HA (1–3 secondaries, auto-failover resuming from the last committed transaction). Result: a dedicated, always-on database with a stable cache and a 99.99% SLA.
  • Specs: 2 GB RAM per CU (112 CU = 224 GB). Up to 6 read replicas on shared storage — no data copies.
  • What a provisioned box typically doesn't give you: second-level branching (copy-on-write, zero duplication), PITR 2–30 days, zero I/O charges, synced tables / Change Data Feed, Unity Catalog governance, native Postgres 16–18.
Real no-gos — state them openly: pure OLTP with no analytics/branching need + hard cross-region DR requirement (not GA yet) + >112 CU single node → Aurora/RDS territory.
Qualify out early

No-go checklist

  • Physically single-tenant hardware requirement
  • >112 CU single node, or writes that must shard horizontally → Aurora Limitless / DSQL
  • Hard cross-region DR requirement (not GA yet)
  • Single-instance logical capacity >2 TB
  • Heavy session-level Postgres feature dependencies with no willingness to adjust pooling
