Objection 01

Autoscaling scales in and out — does the buffer cache go cold every time?

No. Scaling in and out happens in place — no restart, no dropped connections, caches stay warm. Only scale-to-zero empties them. The four cache layers:

1Shared buffers — Postgres process, DRAM. Hot working set; nanosecond access.
2LFC (Local File Cache) — compute node, local NVMe. Warm extension of shared buffers; exists because reads bypass the OS page cache entirely — data arrives over the network from the pageserver, not through a local filesystem, so the OS has nothing to cache.
3Pageserver warm tier — storage service, same region, local NVMe. Materialized pages; survives compute restarts and scale-to-zero.
4Object storage — regional object store, cold tier. System of record: base images + WAL deltas.
  • LFC is custom-built, not the OS page cache. A plain file placed so the OS page cache backs it: DRAM-rich → fully in memory; under pressure → spills to NVMe.
  • Eviction is honest: on scale-down, DRAM shrinks and both tiers evict. What helps is sizing and where misses land: the autoscaler estimates the working set and sizes the cache to it, and the NVMe tier absorbs misses before the pageserver is touched.
  • On fixed computes ≥80 CU (≥18 on Neon), the historic ~1 GB shared-buffer cap (all computes, since launch) is gone: LFC is disabled entirely and shared buffers = 75% of DRAM with huge pages — an 80 CU compute shows shared_buffers = 120GB. Measured: 2× throughput, storage reads 8K→1.5K/s, one workload's CPU 20→4 cores, ~100% cache hit — and no double buffering: 1 GB of cached data costs 1 GB of RAM, not 2. Autoscaling computes still await dynamic shared buffers (roadmap).
Sizing rule: 1 CU = 2 GB RAM. Set min CU to cover the working set — steady-state reads then never leave the machine.

Thresholds: autoscaling ≤ 64 CU (range capped at max − min ≤ 16 CU); scale-to-zero ≤ 32 CU; 65–112 CU is fixed-only — dedicated, always-on, zero scaling movement; from 80 CU, shared buffers take 75% of DRAM.

Honest caveat: scale-to-zero clears layers 1–2 (compute is stateless). Layer 3 survives — first queries hit in-region NVMe, not object storage. Reactivation: a few hundred ms (docs). Production: keep it off; HA doesn't allow it anyway.
Objection 02

LFC vs a regular NVMe cache — and does scale-to-zero clear both?

Why LFC exists: the disaggregated read path bypasses the filesystem entirely — pages arrive over the network from the pageserver — so the OS page cache never sees the data. Postgres needs a cache below shared buffers and nothing provides one — hence LFC.

What it adds:

  • Sized to the working set: the autoscaler estimates working-set size and sizes the cache to it, so the hot set stays on the machine.
  • Resizes with autoscaling, live: the autoscaler adjusts LFC size in step with CU changes while Postgres keeps running. Shared buffers are a static startup parameter — changing them requires a restart. (That's why fixed computes ≥80 CU skip LFC and put the cache in shared buffers: with a fixed size there's nothing to resize.)

The trade-off: LFC is backed by the OS page cache, so hot pages can be held twice (shared buffers + page cache). Fixed computes ≥80 CU remove that by turning LFC off — 1 GB of cached data then costs 1 GB of RAM, not 2.

Scale-to-zero clears layers 1–2 — the compute is stateless. Layers 3–4 untouched. Resumption: a few hundred ms; first queries served from the pageserver warm tier.

Objection 03

Compute/storage separation adds a network hop — throughput suffers at high QPS?

Locate the hop before pricing it:

  • Working-set reads: no hop. Hits in shared buffers/LFC never touch the network.
  • Separation is not exotic. Aurora runs the same shape — compute over a shared, regional, log-structured storage fleet — and resolves the hop the same way: a large local compute cache keeps hot reads off the network.
  • Commit: one cross-AZ WAL hop — every HA database pays this. Aurora's 4/6 quorum and RDS Multi-AZ sync standby are the same class of cost. Aurora is log-is-the-database too (redo records only, never full pages); Lakebase is in the same school — WAL to a safekeeper quorum, no second hop beyond the commit ack.

  • Cold-read-heavy scans far beyond any cache still pay the pageserver round trip. A local-NVMe box wins that benchmark — don't fight it.
  • One writer per branch. Beyond ~112 CU single-node, or write sharding across nodes, the right products are Aurora Limitless / DSQL. Qualify out early — it buys credibility elsewhere.

Objection 04

What about write-heavy workloads?

The write path is where separation usually bleeds — so it gets dedicated engineering:

  • WAL-only commit — compute never ships full pages; the safekeeper quorum acks the log and storage materializes pages in the background.
  • Full-page-image pushdown — Postgres's full-page images after checkpoints (up to 15× WAL inflation, its classic write tax) are moved out of the compute's critical path into storage. Results: up to 5× write throughput (4.5× at 32 vCPU), −94% WAL, 2× lower read tail latency; one production workload went 30 MB/s WAL → 1 MB/s.
  • No I/O charges — Lakebase bills compute and storage (per GB-month) only. Aurora Standard bills per I/O request; Aurora I/O-Optimized drops that for higher instance and storage prices; RDS charges for provisioned IOPS above the gp3 baseline (or on io1/io2).

Honest limits on writes:

  • One writer per branch. The single Postgres writer scales to ~112 CU; beyond that, or for horizontal write sharding, use Aurora Limitless / DSQL.
  • Commit includes the cross-AZ safekeeper ack — bounded but present. If you need sub-ms commits at extreme QPS, benchmark your own path (offer a POC on a branch of their data).
  • For sustained high write QPS: run a fixed size with scale-to-zero off (≥80 CU adds 75%-of-DRAM shared buffers).
Objection 05

Are pageservers shared? Is my data exposed? Do I need to set up CMK myself?

Compute: every compute runs in its own VM (NeonVM, QEMU/KVM) — primary, read replica and HA secondary alike. No shared processes — your buffer cache stays inside that VM, isolated from other tenants.

Storage (safekeepers + pageservers): multi-tenant, regional — like every cloud database's storage fleet, Aurora included. Tenancy is logical: one storage tenant per project, isolated timelines (VLDB §3.5), encrypted at rest and in transit.

CMK — default is system-managed; CMK is opt-in:

  • Default: platform-managed keys. Zero setup.
  • CMK is opt-in: a workspace admin enables it per workspace (Enterprise tier), and new Lakebase projects there are encrypted with your key from your cloud KMS. Revoking the key revokes all access to the data — the auditor's control point.
  • Private Link / private connectivity supported.

Attestations: SOC 2 Type 2 · PCI-DSS and HITRUST in all AWS regions (compliance security profile required) · HIPAA, C5, TISAX via the compliance security profile.

Honest boundary: if a customer mandates physically single-tenant hardware, no managed serverless database qualifies — Lakebase included. Qualify out.
Objection 06

Connection pooling — built-in or build it ourselves? When pooled vs not?

Built-in: Lakebase runs PgBouncer for you. Clients connect to the -pooler endpoint hostname; up to 10,000 concurrent client connections share a smaller server pool. One server connection per transaction, returned on commit.

pool_mode = transaction
max_client_conn = 10000
default_pool_size = 0.9 × max_connections
max_prepared_statements = 1000
query_wait_timeout = 120

Fixed configuration — not customizable.

Pooled when: many short-lived connections — serverless functions, web APIs, per-request ORM connections; or client count above max_connections.

Direct (no -pooler) when: session SET, advisory locks, LISTEN/NOTIFY, SQL-level PREPARE/DEALLOCATE (driver-level prepared statements work; on JDBC set prepareThreshold=0 if errors appear), cross-transaction cursors, session temp tables, pg_dump / migrations — or OAuth roles (pooling supports native password auth only).

App-side responsibilities (both modes): connect timeouts, retry with backoff, never hold transactions across user think-time. With scale-to-zero, retry logic is mandatory — suspension drops every TCP connection; reactivation is a few hundred ms.

Objection 07

My workload is stable — I want provisioned and dedicated. Is Lakebase only for test/bursty?

No. "Serverless is how Lakebase can run, not how it must run."

  • Pick fixed size (0.5–64 CU, or fixed-only 65–112 CU), scale-to-zero off, HA with 1–3 secondaries (auto-failover preserves all committed transactions). Result: dedicated, always-on, stable cache — SLA 99.99% zone-redundant HA / 99.9% single compute.
  • Specs: 2 GB RAM per CU (112 CU = 224 GB); up to 6 read replicas on shared storage, zero data copies, created in seconds.
  • Beyond a provisioned box: second-level branching (copy-on-write), PITR 2–30 days (default 7), zero I/O charges, synced tables / Change Data Feed, Unity Catalog, native Postgres 16–18.
Real no-gos — say them out loud: pure OLTP with no analytics/branching need, cross-region DR with RPO=0/automatic failover (preview only), or >112 CU single-node → Aurora/RDS.
Objection 08

Does Lakebase support HA? And regional DR?

Yes to both — different failure domains, different designs.

High availability (GA): primary + 1–3 secondaries across availability zones.

  • RPO = 0. The promoted secondary continues from the last committed transaction — durability comes from the shared storage quorum, not a replica copy.
  • Automatic failover — promotion needs no new provisioning (standby hardware is always allocated), connection string unchanged, typically seconds.
  • Existing connections are terminated on failover; apps with retry logic reconnect automatically. Secondaries can optionally serve reads via the -ro endpoint.
  • SLA: 99.99% zone-redundant HA / 99.9% single compute. Storage is highly available regardless of the HA setting.
  • Constraints: scale-to-zero unavailable with HA; all instances share the same autoscaling range (max − min ≤ 16 CU).

Regional DR (Private Preview — not yet for production): cross-region replication to a Secondary Workspace.

  • Replication is periodic (minutes-range RPO), happens at the storage layer — the secondary's compute stays idle, so no standby compute cost.
  • Failover is always manual: you promote a possibly-stale copy; unreplicated transactions are preserved as a recovery branch for reconciliation (never auto-merged). New connection string + token required after failover.
  • Not yet: cross-region read replicas, RPO=0 switchover, global endpoint; replication traffic travels encrypted over the public internet.
  • Synced tables and Lakebase CDF pipelines terminate on failover and don't resume automatically — reconfigure them after failing over.

Objection 09

Head-to-head with Aurora Serverless — where does each one actually win?

The one architectural sentence that explains everything: both believe "log is the database" — they differ on where the page of truth lives. Aurora: private quorum storage, single cloud, readable only by that engine. Lakebase (Neon lineage, Gen 3): open-format object storage (S3/ADLS/GCS + Delta) that any engine can read. Everything below follows from that choice.

Where Lakebase wins:

  • Cold start / scale-to-zero: median <500ms to boot a fresh compute (VLDB §5.3) vs Aurora's ~15s instance resume (30s+ after >24h "deep sleep") — a ~30x gap. Lakebase's 4-tier cache waterfall (RAM → local NVMe → warm pageserver → object store) means lower tiers stay warm across compute swaps; Aurora's 2-tier cache dies with the instance.
  • Branching: O(1) metadata operation — fork the storage history at any point, no data copy. Aurora has nothing: copy-then-wait (dump/restore). This is the agent-workload primitive: agents create databases 4× more often than humans, the ecosystem sees >10M new databases daily, production telemetry shows branches >500 deep.
  • OLTP + OLAP in one place: Spark/BI engines read Lakebase pages directly — zero ETL, Unity Catalog governance. Aurora needs DMS/Glue pipelines to feed analytics.
  • True open Postgres: the open-source engine (not a fork) — versions 16/17/18, minor versions tracked to upstream. Aurora is a PG fork with feature gaps.
  • Zero I/O charges: compute + storage only. Aurora Standard bills per I/O request; I/O-Optimized drops that but raises instance/storage rates.
  • Lock-in: open format on any cloud's object storage vs proprietary single-cloud format.

Where Aurora wins — say it before they find it:

  • Track record: 10+ years battle-tested, 99.99% SLA. Lakebase GA'd Jan 2026 (AWS)/Mar 2026 (Azure): 99.9% single-compute, 99.99% with zone-redundant HA. May 2026 us-east-1 AZ incident: 7/8 cells failed over correctly, ~13% of DBs affected; Jan–Apr attainment 99.75–99.85% of DBs met 99.99%. The maturity gap is closing — but it exists.
  • Cross-region DR: Global Database with <1s lag, managed failover, RPO=0 planned switchover. Lakebase DR is Private Preview: periodic replication, minutes-range RPO, manual failover (details in Objection 08).
  • Read replicas: up to 15 independently autoscaling vs Lakebase's 1–3 HA secondaries + up to 6 per branch.
  • Beyond ~112 CU single-node or horizontal write sharding: Aurora Limitless / DSQL territory — qualify out early.

No-go checklist

  • Physically single-tenant hardware requirement
  • >112 CU single node, or writes that must shard horizontally → Aurora Limitless / DSQL
  • Hard cross-region DR with RPO=0 or automatic failover (DR is Private Preview: periodic, manual)
  • Storage far beyond 32 TB on one branch (32 TB default per-branch quota since Aug 2026; larger on request — confirm early)
  • Heavy session-level Postgres feature dependencies with no willingness to adjust pooling
