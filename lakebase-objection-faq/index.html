Objection 01

Autoscaling scales in and out — does the buffer cache go cold every time?

No. Scaling in and out happens in place — no restart, no dropped connections, caches stay warm. Only scale-to-zero empties them. The four cache layers:

1Shared buffers — Postgres process, DRAM. Hot working set; nanosecond access.
2LFC (Local File Cache) — compute node, local NVMe. Warm extension of shared buffers; exists because reads bypass the OS page cache entirely — data arrives over the network from the pageserver, not through a local filesystem, so the OS has nothing to cache.
3Pageserver warm tier — storage service, same region, local NVMe. Materialized pages; survives compute restarts and scale-to-zero.
4Object storage — regional object store, cold tier. System of record: base images + WAL deltas.
  • LFC is custom-built, not the OS page cache. A plain file placed so the OS page cache backs it: DRAM-rich → fully in memory; under pressure → spills to NVMe.
  • Eviction is honest: on scale-down, DRAM shrinks and both tiers evict. The difference is which pages — working-set-aware selection, not blind LRU — and where misses land: the NVMe tier absorbs them before the pageserver is touched.
  • On fixed computes ≥80 CU (≥18 on Neon), the historic ~1 GB shared-buffer cap (all computes, since launch) is gone: LFC is disabled entirely and shared buffers = 75% of DRAM with huge pages — an 80 CU compute shows shared_buffers = 120GB. Measured: 2× throughput, storage reads 8K→1.5K/s, one workload's CPU 20→4 cores, ~100% cache hit. Autoscaling computes still await dynamic shared buffers (roadmap).
Sizing rule: 1 CU = 2 GB RAM. Set min CU to cover the working set — steady-state reads then never leave the machine.

Thresholds: autoscaling ≤ 64 CU (range capped at max − min ≤ 16 CU); scale-to-zero ≤ 32 CU; 65–112 CU is fixed-only — dedicated, always-on, huge stable shared buffer, zero scaling movement.

Honest caveat: scale-to-zero clears layers 1–2 (compute is stateless). Layer 3 survives — first queries hit in-region NVMe, not object storage. Reactivation: a few hundred ms (docs). Production: keep it off; HA doesn't allow it anyway.
Objection 02

LFC vs a regular NVMe cache — and does scale-to-zero clear both?

Why LFC exists: the disaggregated read path bypasses the filesystem entirely — pages arrive over the network from the pageserver — so the OS page cache never sees the data. Postgres needs a cache below shared buffers and nothing provides one — hence LFC.

Side benefits: no double buffering — 1 GB of data costs 1 GB of RAM, not 2.

  • Smarter eviction: the OS page cache evicts blind (generic kernel heuristics); LFC evicts based on which pages Postgres is actually re-reading, so the working set survives longer.
  • Resizes with autoscaling, live: the autoscaler adjusts LFC size in step with CU changes while Postgres keeps running. Shared buffers are a static startup parameter — changing them requires a restart. (That's exactly why fixed computes skip LFC and put the whole cache in shared buffers: with a fixed size there's nothing to resize.)

Scale-to-zero clears layers 1–2 — the compute is stateless. Layers 3–4 untouched. Resumption: a few hundred ms; first queries served from the pageserver warm tier.

Objection 03

Compute/storage separation adds a network hop — throughput suffers at high QPS?

Locate the hop before pricing it:

  • Working-set reads: no hop. Hits in shared buffers/LFC never touch the network.
  • Separation is not exotic. Aurora runs the same shape — compute over a shared, regional, log-structured storage fleet — and resolves the hop the same way: a large local compute cache keeps hot reads off the network.
  • Commit: one cross-AZ WAL hop — every HA database pays this. Aurora's 4/6 quorum and RDS Multi-AZ sync standby are the same class of cost. Aurora is log-is-the-database too (redo records only, never full pages); Lakebase is in the same school — WAL to a safekeeper quorum, no second hop beyond the commit ack.

Published numbers (VLDB 2026 · TPROC-C · p95 ≤ 20 ms · equal durability and latency limits):

Write path: full-page-image pushdown (May 2026) → up to 5× write throughput, −94% WAL, 2× lower read tail latency.

Where the honest limits are:

  • Cold-read-heavy scans far beyond any cache still pay the pageserver round trip. A local-NVMe box wins that benchmark — don't fight it.
  • One writer per branch. Beyond ~112 CU single-node, or write sharding across nodes, the right products are Aurora Limitless / DSQL. Qualify out early — it buys credibility elsewhere.
Sustained high QPS → fixed mode: 75%-of-DRAM shared buffers, huge pages, zero scaling movement. That's the configuration behind the published numbers.
Objection 04

What about write-heavy workloads?

The write path is where separation usually bleeds — so it gets dedicated engineering:

  • WAL-only commit — compute never ships full pages; the safekeeper quorum acks the log and storage materializes pages in the background.
  • Full-page-image pushdown — Postgres's full-page images after checkpoints (up to 15× WAL inflation, its classic write tax) are moved out of the compute's critical path into storage. Results: up to 5× write throughput (4.5× at 32 vCPU), −94% WAL, 2× lower read tail latency; one production workload went 30 MB/s WAL → 1 MB/s.
  • No I/O charges — Aurora/RDS bill per request; Lakebase storage is flat-rate.

Honest limits on writes:

  • One writer per branch. The single Postgres writer scales to ~112 CU; beyond that, or for horizontal write sharding, use Aurora Limitless / DSQL.
  • Commit includes the cross-AZ safekeeper ack — bounded but present. If you need sub-ms commits at extreme QPS, benchmark your own path (offer a POC on a branch of their data).
  • For sustained high write QPS: run fixed mode — that is the configuration these numbers are measured on.
Objection 05

Are pageservers shared? Is my data exposed? Do I need to set up CMK myself?

Compute: one microVM (NeonVM, QEMU/KVM) per project. No shared processes — your buffer cache is physically unreachable by other tenants.

Storage (safekeepers + pageservers): multi-tenant, regional — like every cloud database's storage fleet, Aurora included. Tenancy is logical: one storage tenant per project, isolated timelines (VLDB §3.5), encrypted end-to-end; pageserver access requires the tenant's timeline credentials.

CMK — default is system-managed; CMK is opt-in:

  • Default: platform-managed keys. Zero setup.
  • CMK is opt-in (workspace-level, envelope encryption — your key never leaves your KMS). Revoking the key revokes all access to the data — the auditor's control point.
  • Private Link / private connectivity supported.

Attestations: SOC 2 Type 2 · PCI-DSS and HITRUST supported in all AWS regions · HIPAA, C5, TISAX supported via the compliance security profile.

Honest boundary: if a customer mandates physically single-tenant hardware, no managed serverless database qualifies — Lakebase included. Qualify out.
Objection 06

Connection pooling — built-in or build it ourselves? When pooled vs not?

Built-in: Lakebase runs PgBouncer for you. Clients connect to the -pooler endpoint hostname; up to 10,000 concurrent client connections share a smaller server pool. One server connection per transaction, returned on commit.

pool_mode = transaction
max_client_conn = 10000
default_pool_size = 0.9 × max_connections
max_prepared_statements = 1000
query_wait_timeout = 120

Fixed configuration — not customizable.

Pooled when: many short-lived connections — serverless functions, web APIs, per-request ORM connections; or client count above max_connections.

Direct (no -pooler) when: session SET, advisory locks, LISTEN/NOTIFY, cross-transaction cursors, session temp tables, pg_dump / migrations — or OAuth roles (pooling supports native password auth only).

App-side responsibilities (both modes): connect timeouts, retry with backoff, never hold transactions across user think-time. With scale-to-zero, retry logic is mandatory — suspension drops every TCP connection; reactivation is a few hundred ms.

Connection-breakage matrix:

EventConnections
Autoscaling within min/max rangeNot interrupted — in-place, no restart
Changing min/max CU configurationPossible brief interruption (one-off)
Scale-to-zero suspensionAll dropped; reactivation in a few hundred ms; app retry required
HA failoverAll committed transactions preserved; existing connections are terminated — apps reconnect within seconds with retry logic
Production = scale-to-zero off → only config changes and failovers can break connections.
Objection 07

My workload is stable — I want provisioned and dedicated. Is Lakebase only for test/bursty?

No. "Serverless is how Lakebase can run, not how it must run."

  • Pick fixed size (0.5–64 CU, or fixed-only 65–112 CU), scale-to-zero off, HA with 1–3 secondaries (auto-failover preserves all committed transactions). Result: dedicated, always-on, stable cache — SLA 99.99% zone-redundant HA / 99.9% single compute.
  • Specs: 2 GB RAM per CU (112 CU = 224 GB); up to 6 read replicas on shared storage, zero data copies, created in seconds.
  • Beyond a provisioned box: second-level branching (copy-on-write), PITR 2–30 days (default 7), zero I/O charges, synced tables / Change Data Feed, Unity Catalog, native Postgres 16–18.
Real no-gos — say them out loud: pure OLTP with no analytics/branching need, hard cross-region DR (not GA), or >112 CU single-node → Aurora/RDS.
Qualify out early

No-go checklist

  • Physically single-tenant hardware requirement
  • >112 CU single node, or writes that must shard horizontally → Aurora Limitless / DSQL
  • Hard cross-region DR requirement (not GA yet)
  • Storage needs >8 TB per project (GA limit)
  • Heavy session-level Postgres feature dependencies with no willingness to adjust pooling
