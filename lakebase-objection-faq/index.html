01 · Qualification

Where should we lead, and when should we keep the existing database?

Lead where Postgres transactions meet lakehouse data, agent state or frequent environment creation. Make the value specific: faster development, fewer integrations to operate, or better use of idle capacity. A healthy database with no pain is a weak takeout target.

“Which part of your app lifecycle is expensive today: serving lakehouse data, remembering agent state, creating test environments, or operating a fleet of small databases?”
  1. Who owns the app and the production decision? Bring in the app/platform owner, DBA and security owner alongside the data team. Name the current integration or database budget.
  2. What will grow? A portfolio of apps/agents, or one service with more users and traffic. Database counts alone say little about sustained spend.
  3. What must the first production deployment prove? Agree on p95/p99 latency, concurrency, freshness, recovery objectives, data residency and an acceptable monthly bill.
Qualify carefully: a steady, always-hot OLTP system can run on Lakebase. Displacement still needs a demonstrated benefit that exceeds migration risk. Hard regional DR, extension or hardware requirements can close the opportunity before a benchmark.

Next step: leave with one workload, its owner, its current cost/problem, and a dated proof plan. Use the no-go gates first.

03 · Data & governance

Is this one dataset with no copies or pipelines?

The answer depends on the data path. Synced tables, CDF and Lakehouse//RT solve different problems. Establish which system owns each table's writes before promising an architecture.

Technical detail: copies, freshness and authorization
  • Synced tables (GA): create a managed copy in Postgres. Lakeflow pipelines maintain it and bill pipeline DBUs. Applications should read it; write app state into separate operational tables. Triggered/continuous sync needs source Delta CDF; schema evolution is additive. Validate keys and freshness.
  • Lakebase CDF (Public Preview): captures Postgres row changes into Unity Catalog Delta history tables, with approximately 15-second flushes. A change log still needs downstream logic to derive a current-state table. Flush cadence is not an end-to-end freshness SLA.
  • Lakehouse//RT over Lakebase (Beta): reads materialized columnar data plus recent storage changes against a committed snapshot. The primary supplies an LSN rather than serving the bulk scan. This is a specific enabled capability, not unrestricted Spark access to arbitrary Postgres storage files.

Permissions have two surfaces: Unity Catalog governs analytical/lakehouse access; direct Postgres clients use Postgres roles and GRANT/REVOKE. Do not assume a UC row filter or mask automatically becomes a Postgres policy. Synced-table ownership also restricts owner-only operations such as configuring RLS directly on the synced table.

“We can reduce the integration work. First choose the supported data path, its freshness target, and the permissions each client actually uses.”

04 · Compute posture

Is Lakebase only suitable for bursty workloads?

No. Fixed size and always-on are supported. “Autoscaling” is also the product name; it does not force every endpoint to change size or suspend.

05 · Cache warmth

Does every autoscaling change make the cache cold?

Normal scaling within the configured range happens in place, without restarting Postgres or interrupting connections. Scaling down can still evict pages as memory shrinks. Retaining a running process does not mean retaining every cached page.

Technical detail: the four-layer read path
1Shared buffers: Postgres pages in compute DRAM.
2Local file cache (LFC): a resizable, disk-backed compute cache; Linux page cache can keep its hot pages in RAM.
3Pageserver: materializes page versions from WAL and serves compute-cache misses.
4Object storage: durable storage beneath the pageserver, separate from the compute lifetime.

How is LFC different from ordinary NVMe caching?

Remote page reads bypass the usual local-file read path. LFC supplies a local cache below shared buffers that can resize while Postgres runs. A hot LFC hit can come from the OS page cache; a miss may require NVMe or a pageserver request. NVMe is a medium, not a guarantee that every query stays local.

Large fixed computes: the 9 Sep engineering report says Databricks fixed endpoints ≥80 CU disable LFC and allocate 75% of DRAM to shared buffers, using huge pages. An 80 CU endpoint should report 120GB from SHOW shared_buffers;. That report describes dynamic shared buffers for autoscaling as future work; verify the endpoint rather than extending the fixed-size claim to every size.

Cold-start boundary: suspension/restart loses compute-local state; storage persists. A surviving storage cache can help, but its contents and first-query latency are not guaranteed. Scheduled updates and failure recovery are separate from routine autoscaling.

Proof: measure compute-cache hit rate, storage reads and p99 latency during downscaling and after suspension. Set minimum CU for the hot working set plus query/session memory, not the entire database size.

06 · Network & throughput

Does separated storage add latency at high QPS?

Cache hits stay local; cache misses and durable commits have network work. The question is whether the working set, write rate and client topology meet the application's latency target.

Technical detail: read and commit paths 
Read:   shared buffers → LFC → pageserver → object storage
Commit: Postgres WAL → safekeeper quorum → client acknowledgment
        pageserver materialization happens asynchronously

Compute asks a pageserver for a page at an LSN. The pageserver reconstructs the correct version if needed. Commit waits for durable WAL acknowledgment by a safekeeper quorum, rather than waiting for the final page image in object storage.

Aurora also separates compute and storage. Both designs use local caching, but their storage protocols differ. That shared architecture does not establish equal latency, equal throughput or equal failover behavior.

Benchmark the expensive cases: cold scans beyond cache, large joins that spill, hot-row contention, cross-region clients and sustained write pressure. A cache-friendly microbenchmark is poor evidence for a scan-heavy application.

Proof: run the same schema, indexes, data size, durability configuration and client location. Record committed TPS, p50/p95/p99, errors, cache misses and the monthly cost at the measured capacity.

Evidence: Read & commit architecture · VLDB paper §§3–5, 7 · Aurora storage

07 · Write-heavy systems

Can we claim “5× faster writes than Aurora”?

No. The published improvement compares Lakebase's write path before and after full-page-image pushdown. It is not a competitive speed guarantee.

Technical detail: full-page-image pushdown

Conventional Postgres includes full-page images in WAL after checkpoints to recover from torn page writes. Lakebase's separated storage can generate those images in the pageserver instead of sending them from compute. This reduces WAL traffic while bounding the amount of redo needed to reconstruct a page.

The engineering benchmark reports up to about 5× higher throughput and 94% less WAL traffic; its 32-vCPU comparison measured approximately 4.5×. These are results for the tested workloads and previous implementation. They do not remove locking, index maintenance, query or single-writer limits.

“There is engineering evidence for a more efficient write path. The competitive proof is your transaction mix at your durability and latency target.”

Proof: include WAL-intensive updates, secondary indexes, checkpoint behavior, lock waits and realistic transaction size. Treat the one-writer-per-branch limit as a design constraint.

08 · Isolation & security

Does shared storage mean shared access to my data?

Multi-tenant storage and permission to access another tenant's data are different things. The architecture uses isolated project tenants/timelines and separate compute VMs; it is not a promise of physically dedicated hosts throughout the stack.

Technical detail: authorization, CMK and networking
  • Database access: use least-privilege Postgres roles. Project-management ACLs control infrastructure actions; they do not replace database privileges.
  • Customer-managed keys: Enterprise-tier workspace admins enable Lakebase CMK at workspace level for supported projects. Check the project's status. A project marked Not supported cannot be converted in place; migrate to a new eligible project.
  • Key availability: loss of KMS access makes CMK-managed projects unavailable. Rotation and revocation have different effects; test the recovery runbook.
  • Private access: verify Lakebase's inbound Private Link requirements and actual client routes, including external applications. Workspace private connectivity alone does not prove every database client has a private path.
  • Compliance: AWS documentation lists SOC 2 Type 2 and PCI-DSS/HITRUST support in supported AWS regions, subject to the required compliance profile. Confirm cloud, region, standards and the applicable reports for the deal.
Hardware requirement: if procurement demands dedicated physical hosts, get an explicit architecture attestation. A dedicated compute VM does not satisfy that requirement by itself.

09 · Connections

Is pooling built in, and which clients need direct connections?

Built-in PgBouncer uses transaction pooling for native password roles. Up to 10,000 client connections share a smaller server pool; that is not 10,000 concurrent running transactions. OAuth roles use direct connections.

Technical detail: pooling configuration and session semantics 
pool_mode = transaction
max_client_conn = 10000
default_pool_size ≈ 0.9 × max_connections
max_prepared_statements = 1000
query_wait_timeout = 120 seconds

These settings are managed and not customizable. Copy the -pooler connection string from the Lakebase Connect dialog. Native password connections are disabled by default on new projects; enable them explicitly if the design uses this pooler.

Use direct connections for session-dependent behavior: session-level settings/locks, LISTEN, SQL-level PREPARE, persistent temporary tables, and administrative tools that require session affinity. Protocol-level prepared statements are supported by the configured pooler; validate the actual driver and ORM.

EventClient behavior to design for
Routine autoscaling within rangeNo restart or connection interruption required.
Changing min/max configurationMay briefly interrupt connections.
Suspension, restart or scheduled updateSession state can reset; reconnect and restore required settings.
HA failoverExisting connections terminate; reconnect using the stable primary endpoint.

App responsibilities: bound connect/query/transaction timeouts, keep transactions short and retry with backoff. A lost commit acknowledgment can leave an unknown outcome; use an idempotency key or reconcile before repeating business writes.

10 · HA & regional DR

What survives a compute failure, an AZ outage, or a region outage?

Separate durable storage, in-region compute HA, and regional DR. Each protects a different failure domain. PITR recovers data history; it is not regional failover.

LayerBehaviorBoundary
Storage redundancyCommitted WAL/data outlive the compute; managed independently of compute HA.Durability does not mean queries remain available without a healthy compute.
Compute HA · GA1 primary + 1–3 secondaries across AZs; automatic promotion preserves committed transactions. Stable primary address; clients reconnect.Secondaries are at least primary size; no scale-to-zero. Standalone read replicas are not failover candidates.
Regional DR · Private PreviewPeriodic storage replication to a second-region workspace; manual failover with new connection details. Intended RPO is in the minutes range.Explicitly not intended for production during this preview. No equivalent promise of automatic global failover.
PITR2–30-day history window, default 7. Restore as a new branch.Test the application cutover and recovery time; a restore window is not an RTO.
Technical detail: readable secondaries, DR recovery and SLA

HA secondaries may serve reads through -ro. With only one readable secondary, promotion interrupts that read path until replacement capacity is ready. Dedicated read replicas have separate endpoints and independent sizing; applications that need immediate read-after-write correctness should use the primary.

Regional DR keeps secondary compute idle until promotion, but replicated storage/transfer are separate cost considerations. Unreplicated transactions can be retained as a recovery branch after the original region returns; they are not automatically reconciled into the promoted database. Validate credentials and integration restart procedures in a drill.

SLA: the Databricks SLA credit schedule uses 99.99% for eligible HA endpoints and 99.9% for single-compute endpoints, with covered connection strings and exclusions. It is not a zero-downtime guarantee or a query-latency SLA; Beta use has exclusions. Azure deployments use the applicable Microsoft SLA; verify the cloud-specific agreement.

“We can prove in-region failover today. If production regional recovery is mandatory, resolve that requirement before positioning the DR preview as an answer.”

11 · Branching

Are branches instant, free, and automatically merged?

Branches share storage through copy-on-write; their cost and lifecycle still matter. Parent changes do not automatically flow to children, and child writes do not merge into production.

Technical detail: isolation, reset and billing
  • Branch from current data or retained history. The child has isolated database/role state. Reset refreshes child from parent; apply tested schema changes to production through migration tools.
  • Expiring branches: storage bills for changed data. Permanent branches: bill their full data size even though storage uses copy-on-write. Active branch computes bill separately.
  • Documented project quotas include 500 branches and 20 concurrently active computes by default, with the default branch exempt. Large CI fan-out must budget active endpoints and request quota increases where needed.
Production data in dev: a branch copies the data's sensitivity too. Set access, masking and expiration before granting developers access. Fast creation does not make a production-data clone safe by default.

Proof: create an expiring branch, run a schema test, reset it, and inspect its usage. Compare with Aurora's supported copy-on-write clone workflow rather than assuming Aurora needs a full dump/restore.

Evidence: Branch isolation & billing · Quotas · Aurora cloning

12 · Migration

Can an RDS, Aurora or Azure SQL app move unchanged?

Postgres is the closest starting point; compatibility still requires an inventory. MySQL and SQL Server involve an engine/schema/application migration. Lead with new workloads where a takeout adds little value.

Technical detail: migration gates
  • Lakebase supports Postgres 16, 17 and 18 (17 default). Check extension names/versions, managed-role permissions, SQL behavior, collation, job scheduling and session dependencies.
  • OS access, true Postgres superuser and custom tablespaces are unavailable. databricks_superuser is a managed role, not unrestricted host access.
  • Native Postgres logical replication into or out of Lakebase is not currently supported. A CDF preview does not make Lakebase a native logical-replication subscriber.
  • For a downtime-tolerant move, rehearse dump/restore and validation. For low-downtime migration, validate the exact CDC product and Lakebase target support before promising a cutover window.
  • A project is in its workspace region. Check feature and compliance availability on the target cloud; AWS Singapore/Tokyo and Azure East Asia are relevant regional choices, not interchangeable residency answers.

Exit criteria: a rehearsed cutover, row/count checks and application reconciliation, tested rollback, validated permissions, and an agreed recovery plan.

Evidence: Compatibility & replication limits · AWS regions · Azure regions

13 · Agent retrieval

Can memory, vector search and keyword retrieval live in Postgres?

Yes, where the workload fits the supported search extensions. Lakebase Search is GA: enable it for the project, then install the needed extensions.

Technical detail: search choices and correctness
  • lakebase_vector adds the lakebase_ann vector index with pgvector-compatible types/operators. Embedding generation remains an application/model concern.
  • lakebase_text adds BM25 ranking through lakebase_bm25; combine vector and keyword ranking for hybrid retrieval. lakebase_tokenizer adds text normalization and configurable tokenization.
  • BM25 corpus statistics are computed on index build and maintained by vacuuming. Build against populated data, and validate maintenance after large loads.
  • Transactional consistency of memory does not guarantee retrieval relevance. Measure recall, ranking quality, index-build/maintenance cost and p99 under concurrent writes. Apply tenant access controls to every retrieval path.
“Use one Postgres where that simplifies the app, then prove search quality and isolation. A second search system is a workload decision, not a default requirement.”

Evidence: Search · BM25 maintenance · GA release

15 · Cost

Is Lakebase cheaper, and what belongs in the estimate?

Calculate the actual scenario; there is no universal winner. Separate database spend, data movement and the operational work you expect to reduce. Equal RAM is not equal performance.

Technical detail: Lakebase billing and comparison boundaries
  • Compute bills CU-hours for the primary, HA secondaries and read replicas. Always-On minimum pricing requires scale-to-zero to be disabled for more than 24 consecutive hours; usage above the eligible baseline uses the autoscaling rate.
  • Database storage, PITR history and snapshots are separate meters. Permanent/expiring branch billing differs. Synced tables consume additional serverless pipeline DBUs; transfer/private connectivity can add charges.
  • Rates vary by cloud, region and tier. Keep list, promotion and negotiated discounts separate. The public compute promotion runs to 31 Jan 2027; verify eligibility and the post-promotion budget.
  • Compare the same peak demand, active-hour profile, HA, read capacity, retention and freshness. Aurora provisioned/Serverless v2, Azure SQL provisioned/serverless and storage limits can change the cheapest valid option.

The calculator covers selected public configurations. It excludes tax, support, network charges and separate snapshot charges; it models load and backup growth. Its “n/a” rows can mean the priced configuration does not fit, rather than the vendor cannot support the workload.

“Let's price the production shape, including HA and data movement, then compare measured performance at that cost.”

16 · Expansion

How does a first workload become sustained production use?

Expand validated workloads, not artificial consumption. The two natural shapes are more production apps/teams or more demand on a useful customer-facing service. HA is a reliability decision, not a spend lever.

  1. Land: one app, agent-state store, serving dataset or CI branch workflow. Agree on latency/correctness/cost and the owner who can take it to production.
  2. Production: validate access, recovery, observability and capacity; choose HA according to the service requirement.
  3. Expand: repeat across teams or scale proven traffic. Track active usage and production adoption rather than the number of created databases.
  4. Standardize: shared templates, connection/retry practices, branch policies, budgets and an incident runbook. Reassess cost after the promotion.

18 · Decision gates

Which requirements should stop or reshape the opportunity?

  • Production regional DR that the current service cannot meet. The Private Preview is not a substitute for an approved production recovery design.
  • Horizontal write scale-out or capacity beyond the single writer. Evaluate a purpose-built distributed/sharded database; Aurora Limitless and Aurora DSQL are separate designs, not drop-in extensions of every Aurora PostgreSQL app.
  • Mandatory native logical replication, unsupported extensions, unrestricted superuser/OS access or tablespaces. Resolve compatibility before promising migration.
  • Physical single-tenancy, residency or compliance requirements without a confirmed supported deployment. Validate against cloud-specific service documentation and contracts.
  • Unapproved large-data/compute quotas. The current project documentation lists storage quota as adjustable, not a universal 8 TB or 32 TB ceiling. Confirm the project's actual quota; an increase takes effect on compute start/restart.
  • No measurable reason to replace a healthy existing system. Start with a new adjacent workload or leave the incumbent in place.

Qualify sharply. Prove the architecture. Price the whole workload.

Lead with a concrete app problem, answer objections with a documented boundary, and close on the customer's measured production criteria.
